# 2026-10-19 物理步成本：release 包对照与单位数扩展曲线

status: closed（测量完成；结论供"物理步要不要迁到 C# / GDExtension"决策，未改游戏逻辑）

返回 [Handoffs 索引](README.md)。前置背景见 [2026-10-17 性能诊断与 C# 迁移待办](2026-10-17-performance-diagnosis.md)。

## 1. 结论

**release 包比 tools 版快多少？** 东京 C2（48 名演员，其中 33 架飞机）4 对 4 交错：

- 物理步脚本 3.98 → 3.28 ms/步，**快约 17.5%**；单步 p99 5.47 → 4.50 ms。
- 平均帧率 140 → 171 FPS（+22%）。有物理步的帧均值 10.39 → 9.16 ms，无物理步的帧 4.70 → 4.07 ms。
- 有物理步帧的 p99 两侧都是 15.18 ms；>16.7 ms 帧两侧都在 0.1–0.2%，差别在轮间噪声内。C2 剩下的慢帧主要是事件型（地图换切面等），release 救不了。
- 收益只落在 GDScript：飞机物理、AI、雷达、子弹这些桶 ×0.78–0.85；渲染提交（2.11 vs 2.07 ms）和物理步后的引擎段（0.130 vs 0.133 ms/步）不变。
- 加到 150/200 单位时，物理步脚本仍快 18–20%（12.03 → 9.91、16.63 → 13.38 ms/步）。但 release 在重载下有一种**间歇出现**的原生开销：`phys_engine` 每步高 60–75%，`proc_signal`、`pre_render` 每帧各多 1–2.5 ms。84 单位以上 10 轮里 7 轮出现，tools 14 轮一次都没有（见 §5.3），出现时会把整帧收益抵掉一大半。

**按现在的 GDScript，60 帧能撑多少架飞机？** 以 C2 的海陆空配比（每 10 架飞机约配 4 个地面单位、2–3 艘舰），24 km 战场，固定镜头巡检：

| 判据 | tools | release |
|---|---|---|
| 有物理步帧 p99 ≤ 16.7 ms | 约 38 架（约 53 演员） | 约 40 架（约 55 演员） |
| >16.7 ms 帧 ≤ 1% | 约 36 架（约 51 演员） | 约 43 架（60 演员档两轮 0.41% / 1.14%） |
| 有物理步帧均值 ≤ 16.7 ms | 约 55 架（84 演员档 16.77 ms） | 约 57 架 |
| 平均帧率 ≥ 60 | 约 57 架 | 约 60 架（61 架档四轮 48–70 FPS，离散大） |
| 物理步满 60 步/秒（模拟不减速） | 61 架 59.8 步/秒，77 架降到 55.6 | 61 架 59.8 步/秒，97 架降到 47.0 |

- 想"几乎不掉帧"，现在的上限约 **36–38 架**。C2 的 33 架已经用掉约 90%，release 只把这条线推到 40–43 架。
- 只要平均守住 60 帧，上限约 **55–57 架**。到 61 架进入补步连锁：一轮约 400 帧要补第二步，74% 的帧超 16.7 ms。77 架时物理步只剩 55.6 步/秒，模拟时间开始变慢。
- 每架飞机每物理步的全部脚本成本：tools 约 **120 µs**（33 架）到 129 µs（129 架），release 100–104 µs。其中飞机自身（`aircraft_phys`）约占 70–76%（33 架时约 92 µs/架），AI 约 4–6%。边际成本随规模上升：tools 从 0.11 ms/架（33 架）到 0.15 ms/架（129 架）。超线性来自两处 O(N²) 结构：子弹物理占比 3% → 12%，雷达锁定 3% → 8.5%（雷达配对 10 → 917 次/帧）。
- **对迁移决策的含义**：拐点由物理步脚本和随单位数增长的其余帧开销共同决定。其余部分（物理步请求的重绘冲刷、`_process`、延迟调用、渲染）在 33 架时约 6.4 ms，每多一架约增加 0.16 ms，也大多是 GDScript。只迁物理和 AI、假设这部分快 4 倍，"均值 60 帧"的上限从约 55 架升到约 75 架，"p99 不掉帧"从约 38 架升到约 53 架；只快 2 倍则约为 67 架和 47 架（§6 估算）。release 的 17% 远不够，而且两条 O(N²) 路径换语言只能缩小常数。

## 2. 环境与方法

- **机器**：Ryzen 9 9955HX（16C/32T）+ RTX 5070 Ti Laptop，空闲 RAM 约 17 GB。同时接着 Oray 远程虚拟屏（60 Hz）。
- **两侧构建**：tools = Steam 版 `godot.windows.opt.tools.64.exe`（`4.7.2-stable (steam)`，GDScript 跑 debug 路径）；release = 官方 4.7.2.stable 导出模板（`4.7.2-stable (official)`）。用同一份工作树（`0d3af0a` 加本 PR 的测量改动），由 Godot 4.7.2 编辑器在 Shadow 副本里导出 `Windows Desktop` 预设。
- **场景**：`tokyo_volume_c2`，Shadow Visual，1600×900 离屏窗口，36 s bench 时长，M20 安装包（package SHA `424e4aa1…d858`）。探针统计 bench 物理时钟 `bench_t ∈ [3, 36)` 的帧，起点与东京 runner 的墙钟采样一致；每轮探针帧率与 runner 自带的 `tokyo_wall_clock.avg_fps` 逐轮相符。
- **VSync 关闭**（`AGL_TOKYO_DIAGNOSTIC_VSYNC=off`，两侧一致）。离屏窗口落在 Oray 的 60 Hz 虚拟屏上，开 VSync 时 C2 被锁在约 59.9 FPS（`refresh_hz=60`），帧时被量化，没法比较有物理步和无物理步的帧。所以本稿的帧率比 2026-10-18 那批（约 127 FPS，当时按 300 Hz 屏）高，两批数字不能直接比。其余设置照常：补步上限 2、物理插值开、无帧率上限。
- **user:// 隔离**：每轮把 Godot 的 `APPDATA` 指向父会话 user:// 备份的副本（`scratchpad\appdata_iso`），真实 `%APPDATA%\Godot\app_userdata\AGL` 测量前后 23 个文件逐项一致。原始备份只读，没有改动。
- **环境变量残留**：每轮单独生成 `.cmd`，先在 cmd 层 `for /f … set "%%V="` 清掉全部 `AGL_*` 再显式设置，并逐轮导出审计；所有轮次 err 里都没有 `[Autoplay] armed`。
- **机器安静**：另一会话 10:54 结束后才开始；每轮启动前要求连续无外部 `godot*` 进程（首轮 60 s、其余 10 s），全程持有共享笔记的 `godot-machine.lock.md`。
- **排序**：A/B 用 ABBA（T R R T T R R T）；扩展档按升序再降序；最后一批在同一批内交错 96 / 200 单位的 tools 与 release，并补一对 48。

单位数用新诊断开关 `AGL_TOKYO_BENCH_COMPOSITION="战斗机:直升机:火炮:舰船"`（每侧）调整，只作用于 C2。战场跨度固定 12000 px（24 km）、镜头巡检节拍不变，所以密度随单位数上升，与正式局"同一战场更多敌人"一致。固定部分是两组防空锚点（各 AA+SAM）加一对轰炸机。下表的飞机、地面、舰数是采样起点的实测普查（`tokyo_unit_census_start`，飞机含玩家观察机），mixed 样本全员无敌，数量全程不变。

各指标的口径（来自 `scripts/diagnostics/frame_probe.gd` 的互斥阶段）：

- `phys_script`：全部 `_physics_process` 脚本段。每步成本 = 窗口内总和 ÷ 物理步数。
- `phys_engine`：物理步脚本段之后的引擎工作。
- `proc_signal`：process 信号段，物理步里请求的重绘在这里冲刷执行。
- `proc_script`、`pre_render`、`render`、`post`：依次是 `_process` 脚本段、渲染前的延迟调用与释放、渲染提交、其余时间。
- 有/无物理步帧按该帧 `steps ≥ 1` 分组。百分位用 nearest-rank。

## 3. release 包：导出与 M20 加载

- **按现有方式把 M20 打进 PCK，导不出来。** 原 preset 会把 M20 的 106,789 个 `.res` 全部打进 PCK。编辑器首次扫描用了约 26 分钟，写入 7.9 GB 数据约 16 分钟。之后在最后一个 `.remap` 写完的收尾阶段单核空转超过 60 分钟、零 IO，临时 PCK 一直没改名，最后被看门狗回收（总计 105 分钟）。
- **实际用的做法。** 从不含 M20 的工作树副本导出（其余资源仍按现有 preset 进 PCK），用时 59 s，产出 `AGL.exe` 加 192 MB `AGL.pck`。运行时在程序目录放 `resources/maps/tokyo_playable` 的 junction。导出包里 PCK 没有的 `res://` 文件会回落到"当前工作目录 + 相对路径"读取，launcher 把工作目录设为程序目录。M20 由此按原路径 `res://resources/maps/tokyo_playable/m20/package.json` 加载，地图状态 `hlod=true active=true`。C2 的 HLOD 统计两侧一致：隐藏、超预算、未覆盖帧都是 0，待交接帧 364–389，切换 261–290 次。
- **两点注意。** 这只能证明运行时代码在导出包里能加载 M20，不是发行方案：依赖工作目录，玩家从快捷方式启动时未必成立。前 3 批的 junction 指向 D 盘主检出；最后一批（b7）改指 tools 侧所用的同一份 C 盘影子副本，用来排除存储差异，release 的间歇原生开销照样出现（§5.3）。
- **release 现有缺陷：飞机剪影读不到。** `*_detail.png` 有 `.import`，导出时只打包导入产物，原图不进 PCK。`aircraft_silhouette_catalog.gd` 的 `_texture_for` 用 `FileAccess.get_file_as_bytes` 直读原图，失败后不缓存，于是每次绘制都重试并 `push_warning`：一局 8,583 次，约 200 次/秒。release 包里的飞机因此退回旧多边形图标。测量时在程序目录放了剪影目录的 junction，绕开这个问题，告警归零；首轮冒烟（受影响）未计入对照。修复属于游戏代码，不在本稿范围（见 §7）。
- **探针与结果输出。** 导出包里 `res://` 只读。`frame_probe.gd`、`bench_runner.gd` 和东京 runner 的截图改为在非编辑器构建写 `user://bench/results/`（与 EventLogger 的切换口径一致），launcher 结束后把本次文件搬回项目 `bench/results/`。

### 5.3 release 在重载下的间歇原生开销

以 tools 同档中位数为基准，比较每轮的 `phys_engine`/步：

- tools 84–200 单位 14 轮全部在 0.97–1.04 倍。
- release 84 单位以上 10 轮里 7 轮在 1.61–1.76 倍，其余 3 轮在 0.99–1.07 倍，呈双峰。
- 抬高的轮次里 `proc_signal` 和 `pre_render` 同时高出 1–2.5 ms/帧。例如 release 200 单位两轮都满补步：b7-06 为 `phys_engine` 0.378 ms/步、20.1 FPS，b7-07 为 0.616 ms/步、18.5 FPS。
- 72 单位及以下两侧原生阶段一致。

两侧的工作量逐轮相同：每步增删节点数、节点数、对象数和 Canvas 绘制数都一致。最后一批把 release 的 M20 改读同一份 C 盘副本后仍然出现，所以与存储位置无关。根因未定位，可能与线程/核心调度或分配器行为有关，需要原生剖析。它让 release 在 96 单位时的轮间帧率从 48 到 70 FPS 不等。迁移后的验收必须用 release 包、多轮测，不能只看一轮。

## 6. 拟合与迁移估算

物理步脚本时间对飞机数 N 的最小二乘拟合（C2 配比，各档均值）：

- tools：`phys ≈ 0.66 + 0.0945·N + 0.000229·N² ms`（8 档，残差 ≤ 0.1 ms）
- release：`phys ≈ 0.27 + 0.0865·N + 0.000128·N² ms`（7 档）

线性拟合的斜率：tools 0.132 ms/架、release 0.107 ms/架。

有物理步帧中物理步以外的开销（`有步帧均值 − phys_script`），tools 在 33–55 架之间约为 `6.44 + 0.16·(N − 33) ms`：

- 主要随单位数增长的是 `proc_signal`（物理步请求的重绘）、`proc_script`、`pre_render`，三者合计每多一架约 +0.13 ms，渲染每多一架约 +0.02 ms。
- C2 实测 p99 比均值高约 4.6 ms，多为地图换切面等事件型开销。

**估算（不是测量）**：假设 `aircraft_phys` 加 `ai_tick`（合计约占物理步脚本的 82%）迁移后快 4 倍，其余代码不变，物理步脚本约降到原来的 0.385。

- "有物理步帧均值 ≤ 16.7 ms"：约 55 架 → 约 75 架。
- 按 C2 的 p99 余量推，"p99 ≤ 16.7 ms"：约 38 架 → 约 53 架。
- 若只得到 2 倍，分别约为 67 架和 47 架。
- 同一模型代回现状（不加速）得到约 55.6 架和约 39 架，与实测的约 55 架、约 38 架相符。

估算没有计入 C# 与引擎互调的封送成本和 GC 停顿（约束见 [2026-10-17 诊断 §4](2026-10-17-performance-diagnosis.md)）。也没有计入 `bullet_phys`、`radar_locks` 的 N² 增长：迁移只缩常数，规模再大仍要改算法。

## 7. 本次发现的问题与后续

1. **release 包剪影 PNG 读不到（现有缺陷）**：见 §3。修法方向：失败结果做负缓存；改走导入后的纹理，或把这批 PNG 的导入方式设为原样保留。修完要在导出包里验证剪影可见、告警为零。
   - 2026-10-19 已修：改走导入纹理并按 key 负缓存，导出包验收见 [飞机顶视轮廓 spec v12](../specs/systems/aircraft-top-view-silhouettes.md)。之后跑导出包不再需要剪影目录 junction。
2. **M20 无法按现有 preset 打进 PCK**：见 §3。发行前需要单独的分发方案，例如 M20 放程序目录外的独立目录并用基于可执行文件路径的绝对挂载，或拆成单独 PCK 运行时 `load_resource_pack`。同时记录或规避 4.7.2 导出 10 万级文件时的收尾空转。
3. **release 在重载下的间歇原生开销**：见 §5.3，需要原生剖析（ETW/Superluminal 一类）确认来源，再判断迁移后的 release 包会不会继承。
4. **两条 O(N²) 路径**：`bullet_phys`（子弹缓存网格/碰撞）和 `radar_locks`（配对数随 N² 增长），规模化时应先改算法。
5. 本稿的帧率在 VSync 关闭下测得；60 Hz 虚拟屏开着时，常规 bench 会被锁在 60 FPS（已写入共享笔记的测量陷阱）。
