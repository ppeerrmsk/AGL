# 大规模战斗 60 FPS 路线

> 状态：2026-08-20 第一轮已执行；完成逐帧诊断、低风险热路径优化、正式 C1/C2 镜头修正与专项门扩充。
> 本文不是战斗群 AI 的 approved spec。涉及 AI 权威、远距结算或精确/简化切换前，必须另立系统 spec 定稿。

## 1. 当前结论

AGL 当前能以很高的平均帧率运行 36 名全可见混合战场和 48 名/24 km 多战线场；修正 bench
镜头权威并完成第一轮优化后，两门的 1% low 已分别达到 80.00 / 70.48 FPS，但仍各有 1–2 个
孤立帧低于 60，因此还不能宣称“严格硬 60 FPS 达标”。继续扩大为 60 名
全可见演员后，问题从偶发尖峰变为持续超预算；72/96 名全可见不是当前架构能直接承担的负载。

正式三次基线：

| 场景 | 负载 | avg FPS 中位 | 1% low 中位 | worst 中位 | <60 帧中位 | 裁定 |
|---|---|---:|---:|---:|---:|---|
| C1 | 36 名 / 8 km / 全可见 | 121.51 | 60.00 | 42.69 | 17 | 失败：周期性尖峰 |
| C2 | 48 名 / 24 km / 多战线 LOD | 117.19 | 60.00 | 39.92 | 20 | 失败：周期性尖峰 |

C2 三次均为 Godot 4.7.2、GL Compatibility、RTX 3080、`Shadow Visual`；每次保持
`live_members=48`、`span_km=24.0`、`shells=9`。末秒 74–77 个 CombatUnit、2–3 枚导弹，
但其中两次为零普通子弹，故 C2 只证明多战线/LOD 与全局扫描成本，不代替近景弹幕门。

> 基线勘误：旧 C1/C2 setup 直接写 `Camera2D.zoom`，下一帧会被 `CameraController` 的
> `_base_zoom/target_zoom` 恢复成 0.35。旧数据仍可用于同实现下的 A/B，但不能作为 0.20 战略视距合同。
> 新 bench 通过 `_bench_set_camera_zoom()` 同步三处权威；当前 C1 实际 0.263，C2 实际 0.20。

单次探索性全可见容量曲线（用于找拐点，不是三次正式验收）：

| 气氛演员 | 末秒 CombatUnit | avg FPS | 1% low | worst | <60 帧 |
|---:|---:|---:|---:|---:|---:|
| 48 | 76 | 91.50 | 46.67 | 38.47 | 89 |
| 52 | 81 | 77.20 | 34.92 | 28.66 | 177 |
| 56 | 88 | 65.74 | 32.73 | 26.26 | 260 |
| 60 | 93 | 54.36 | 30.00 | 25.96 | 534 |
| 72 | 111 | 48.61 | 21.92 | 17.83 | 555 |
| 96 | 145 | 36.12 | 17.19 | 15.88 | 601 |

因此当前全精度容量拐点在 52–60 名之间：56 名的平均值仍略高于 60，但低帧已经严重失败；
60 名连平均值也不再达标。

## 2. 交付目标

“大规模”拆成近景全精度和全地图多战线两个合同，避免用一个人数掩盖不同成本形状。

### G0：现有基线清债

- C1 36 名/8 km 全可见与 C2 48 名/24 km 连续三次 `Shadow Visual`；
- 每次 `frames_below_60 == 0`、`p1_fps >= 60`、`worst_frame_fps >= 60`；
- 实际演员、弹丸、标签、尾迹、地图、天气与 HUD 达到负载合同；
- 先完成 G0，才允许用更大人口评价容量收益。

### G1：60 名近景全精度战斗

- `live_members >= 60`，8 km 主交战带，全员真实移动、索敌、开火、受击与脱离；
- 末秒参考下限：约 90 个 CombatUnit、90 发普通弹、8 枚导弹、7 枚气氛炮弹；
- 不得以演员死亡、停火、关闭尾迹/标签/爆炸或把成员移出镜头达标；
- 三次 30 秒 Visual 全部守住 60，再追加 S1 弹幕与 S2 BOSS 专项。

### G2：72 名全地图多战线

- 24–48 km 内至少三个同时活跃战斗群，地图上持续可见移动、开火、烟迹、爆炸与战线变化；
- 玩家附近 24–36 名维持个体级精确模拟，其余成员可进入经 approved spec 定义的战斗群级调度；
- 玩家点名、接近或介入时必须无缝回到精确模拟，保存成员、HP、弹药、航向、编队与目标语义；
- 玩家、玩家指挥目标、BOSS 与显式关键单位永不降级；不得瞬移、全队同步转向或生成虚假命中。

96 名作为 G2 通过后的伸展目标，不阻塞第一阶段交付。

## 3. 全域覆盖合同

性能容量不能只按飞机数定义。正式门必须覆盖当前数据源中的**每一种可生成类型**，并让其专属成本
实际触发；仅成功实例化、处在画外、没有目标、没有开火或技能未触发，都不计入覆盖。

### 3.1 自动覆盖清单

建立生成式 `performance_coverage_manifest`，只引用当前权威注册表，不在规划里冻结数量：

- `EnemyPoolRegistry.ROWS` 的每一行常规敌机，以及 `enemy-index` 登记的事件/BOSS 专属机、轰炸机、
  旋翼机、UAV/UCAV、电子战支援、王牌和动态转阵营单位；
- `BossRegistry` 的每一个当前 BOSS id；
- 玩家直属小队、战区一次性空中支援、AWACS/第三方 ALLY、护送轰炸编队、投降转 ALLY 与
  BOSS Debug 正式构筑友军；
- SAM、AAA、RadarStation、StrategicTarget、气氛 SPG、机场/战区静态目标和 BOSS 挂点；
- FFG、DDG、CG、CV、舰载挂点、CIWS/VLS/Flak 与水面巡逻/驻泊两种更新路径；
- `SurvivorData` 正式技能表中的每一项技能及其 `max_stacks`、装备前置和真实触发条件；
- 天气、云/沙尘、地图底图、尾迹、标签、爆炸、AOE、命中闪光、锁定线、HUD、Tab、
  无线电队列、字幕排版、音效并发和 BOSS 演出通道。

CI 审计必须保证每个注册项至少映射到一个可运行场景和一个成本标签；新增类型或技能而未登记时直接失败。
场景可以按 shard 分批，不要求把全部类型同时塞进一个失真的大杂烩，但发布候选必须跑完整 shard 集。

### 3.2 敌机与友军

| 成本族 | 必须激活的行为 | 最低证据 |
|---|---|---|
| 常规固定翼 | 全功能 BFM、simple AI、BVR、joust、编队、脱离/重整、机炮/导弹/火箭 | registry shard 全类型轮转 + C1/G1 最坏混编 |
| 特殊空中单位 | 轰炸投弹、旋翼悬停/扫射、UAV 蜂群、电子战场、激光反导、忠诚僚机/自爆拦截 | 每种专属消费路径至少一次真实触发 |
| 敌方王牌/事件机 | Wraith 角色、非 BOSS 王牌、Orion、Snowblind、DEADAIR、投降转阵营 | 事件专项 + C2/G2 同窗 |
| 玩家与友军 | 当前操控机、2–8 僚机、FREE/FOLLOW/GUARD、切控、战区支援、AWACS、护送编队 | `zone_support_stress` 扩展版 + 满编技能构筑 |

全类型轮转用于防漏接资源、子节点和特殊更新；性能裁定仍取每个成本族实测最坏的混编，不能用大量
最便宜 `simple_ai` 单位稀释昂贵类型。

### 3.3 地面与海面

- 地面门同时维持 SAM 锁定/发射、AAA 炮塔追踪、RadarStation 数据链、可移动 GroundUnit、
  战略 TGT、双方气氛 SPG、建筑遮挡和空对地攻击 pass；必须记录各类存活数、扫描数和实际弹量。
- 海面门同时维持 FFG/DDG/CG/CV、全部 MountTarget、CIWS 真弹拦截、VLS、Flak、舰炮、
  舰载机弹射、弱点/挂点受击与巡逻转向；`naval_zone_stress` 需升级为严格 Visual 分位门。
- 地面/海面不能只作为静态背景。样本结束时至少存在持续索敌、锁定、开火、命中或拦截事件。

### 3.4 全部 BOSS

四类当前 BOSS 分别保留独立最坏态，不能只用 Black Star 代表：

| BOSS | 最坏成本态 |
|---|---|
| Wraith Squadron | 四机队级战术、包夹/重整、YF-23 强化支援、全套标签/锁定/无线电 |
| Carrier Strike Group | 最大通关强化护航编成、CV/CG/DDG/FFG 全挂点、CIWS/VLS/Flak、8 架舰载机、Poltergeist 二阶段 |
| Mother Goose | 10 挂点/弱点、30 UAV 上限、MQ-X、JAM 场、VLS 空爆、激光反导、20 友军压力 |
| Black Star | 双树 16 个 G3 终态、再入/状态栏/AOE/冲击波/齐射，并与现有 Sentinel/5 护卫同窗 |

现有 Black Star `boss_hyper_a_stress` 可继续使用；Wraith、CSG、Mother Goose 要补同格式的
30 秒 `Shadow Visual` 场景和统一 avg/p1/worst/<60 输出。登场演出另跑 transition 门，避免稳态高帧
掩盖横幅、镜头、舞台隔离、音频与无线电首次构建尖峰。

### 3.5 气氛、特殊效果、无线电与音频

- C1/G1 必须同时存在空战、炮战、海战气氛，尾迹、曳光、导弹、炮弹、爆炸、烟团、AOE、
  命中闪光、数据标签、锁定线、天气和 HUD 全部开启。
- 天气/地图用云、沙尘、底图、detail/Operational、Tab 与 transition/cold 分开 A/B；
  透明层与大范围 fill 不能只看脚本桶。
- 无线电必须测试真实 trigger：普通环境台词、击杀/减员、战区通报、友军进离场、护送、
  BOSS scripted sequence 同时入队；覆盖本地化 `_FMT`、长文本布局、队列淘汰和字幕淡入淡出。
- 音频记录同帧 SFX/语音请求数、活跃播放器数和首次加载；没有语音素材的路径仍要测试字幕与
  队列成本，未来加入素材后必须重新建立 cold/steady 基线。
- bench 结果新增 `trails/labels/explosions/aoe/radio_lines/audio_players/weather_layers` 等合同计数；
  任一关键计数为 0 时不能宣称覆盖。

### 3.6 全部技能

功能性的 `skill_audit` / `skills720` 保留，但性能另建 registry-driven 技能成本矩阵。每项技能至少有
一个成本标签，并按正式 `max_stacks`、真实装备和真实触发条件运行：

1. **每机/每帧状态**：机动、速度/G/失速访问器、状态效果、CD、锁定线和标签；
2. **全队/全场扫描**：光环、ESM、雷达/副雷达、多目标锁定、敌我状态广播；
3. **弹丸放大**：多锁齐射、QMAAM、火箭齐射、CIWS、连锁/穿透、AOE、空爆、地雷；
4. **实体放大**：忠诚僚机、召唤物、支援与技能生成节点；
5. **视觉/HUD 放大**：尾迹、范围圈、状态层、充能条、威胁提示、伤害反馈；
6. **事件尖峰**：击杀、受伤、僚机阵亡、升级/进化、切控与奖励触发的批量重算。

每个标签族建立“空构筑 baseline / 单技能满层 / 合法最坏组合”三联 A/B。合法最坏组合必须尊重
互斥、装备和机型门控，不制造正式局不可能出现的假负载；同时要覆盖玩家当前机、僚机和敌方消费端。
新增技能若引入 tick、draw、实体、弹丸或全场扫描，未给出对应性能场景则不得进入正式池。

## 4. 暂定帧预算

总预算为 16.67 ms。以下是 60 名近景门的主线程暂定上限；P0 时序采样完成后再用真实分位校准，
不能拿一秒均值代替单帧预算。

| 成本域 | 暂定上限 | 当前 60 名末秒参考 | 说明 |
|---|---:|---:|---|
| Aircraft 物理 + 武器 + 状态 | 2.5 ms | 3.67 ms | 保留位置/航向 60 Hz；慢量与重复查询降频 |
| Aircraft 绘制命令构建 | 1.5 ms | 4.35 ms | 静态机体与动态覆盖层拆分 |
| 尾迹绘制命令构建 | 0.5 ms | 2.99 ms | 世界系缓存或集中批处理，不逐帧重建全部点 |
| 子弹/导弹物理与命中 | 1.5 ms | 1.44 ms | 当前弹量不算极端，S1 另设更高弹量门 |
| AI、雷达、战区/天气/地图/HUD | 2.0 ms | 覆盖不完整 | 必须补逐帧归因 |
| 引擎、渲染提交、GPU、尖峰余量 | 8.67 ms | 尚未拆出 | 作为不能提前花掉的安全余量 |

当前 PerfBuckets 以“一秒总耗时 / 渲染帧数”显示；当渲染低于 60 而物理仍追赶时会放大每渲染帧数值。
新采样必须同时记录渲染帧和物理 tick，按单帧时间线归因。

## 5. 根因假设与证据强度

### 已有直接证据

1. **36/48 名的主要失败是尖峰，不是平均算力**：两种负载平均都高于 110 FPS，但最差帧只有约 40 FPS。
2. **60 名以上存在持续成本墙**：60 名平均降到 54.36 FPS，72/96 名继续单调下降。
3. **高密度时主要可见桶随规模增长**：Aircraft draw、Aircraft physics、Trail draw、Bullet physics 是 60–96 名的稳定大项。
4. **尾迹每个渲染帧重建几何**：每条尾迹重新分配顶点/颜色/索引数组，并对最多 80 个世界点做 `to_local`；
   60 名样本约 2.99 ms，96 名约 3.36 ms。
5. **飞机绘制是当前最大单项之一**：48/60/96 名末秒约 2.09/4.35/7.50 ms。
6. **弹丸热路径仍是 Dictionary + 逐弹循环**：子弹每物理帧重建 UnitGrid 并更新 Dictionary；
   96 名样本 116 发子弹已约 3.90 ms/渲染帧。
7. **仍有高频节点扫描和无条件重绘**：AI 节流门前会经 `aircraft.get_herbst()` 扫子节点；
   AA/雷达站仍扫描父场景；Ground/SAM/AA/Radar 多条路径每物理帧 `queue_redraw()`。
8. **导弹命中仍是 M×N 候选循环**：MissileManager 逐导弹扫 `target_list`，另有多处 `get_children()` 统计。

### 仍需逐帧证据的假设

- C1/C2 每秒级尖峰可能来自生成/释放、周期性全场任务、日志/字符串分配、性能快照、音频、
  Canvas 重建或物理追赶；现有“最后一秒平均桶”无法裁决。
- C2 末秒无普通子弹仍出现相同级别尖峰，说明普通子弹不是尖峰成立的必要条件，但不能排除
  早先弹幕或其它周期事件。
- PerfBuckets 本身在高频路径进行计时与 Dictionary 累加，并每秒复制快照；必须测量 observer tax，
  不能默认诊断工具零成本。

## 6. 实施顺序

### P0：先抓住尖峰

1. 给 bench 增加逐帧环形时间线：render delta、physics tick 数、各桶当帧总量/最大值、单位/弹丸数、
   draw object/call 指标，以及 spawn/free、锁定轮转、重定向、爆炸、音频和日志事件标记。
2. 当帧超过 16.67 ms 时，保留前 120 帧和后 30 帧；报告 p95/p99/max，而非只写最后一秒均值。
3. 做 PerfBuckets 关闭/开启、细桶采样 1/N、EventLogger 关闭/开启的同负载 A/B，量化观察者成本。
4. 对 C1/C2 做武器、尾迹、标签、爆炸逐层 ablation；每次只关一层并保持演员与运动不变，
   用来定位尖峰，不把关闭内容当最终优化。
5. P0 结束条件：至少 80% 的 `<60` 帧能归到明确事件/桶，且剩余未知尖峰单次不超过 16.67 ms。

### P1：低风险热路径清理

1. **尾迹世界系缓存**：让尾迹 CanvasItem 不继承飞机变换，或集中到世界级 TrailBatchRenderer；
   只在 20 Hz 采样新增点、颜色/状态改变或可见性切换时更新几何，保留屏外剔除与回屏淡入。
2. **缓存组件引用**：Herbst/Maneuver/装备节点在创建或换装时登记，禁止 AI/Aircraft 高频扫描子节点。
3. **清掉场景树扫描**：AA、雷达站和其它低频索敌改读维护列表/分桶；保留 `is_instance_valid` 边界。
4. **状态驱动重绘**：SAM/静态地面本体只在状态变化时重绘；旋转炮塔/雷达盘拆成独立轻量动画层，
   不让动画迫使整个单位标签、范围圈和本体重建。
5. **诊断开销隔离**：发布态关闭细粒度桶；bench 采用低观察者开销的预分配采样。

P1 先回归 C1/C2；G0 未过，不进入更大规模结论。

### P2：渲染与弹丸数据路径

1. AircraftRenderer 拆分静态轮廓/固定挂点与动态锁定、受击、标签覆盖层；静态层复用 Canvas 命令，
   动态层按状态和 LOD 重绘。
2. 对同类远距标签、威胁线和装饰标记做批提交；不能牺牲玩家、当前目标、BOSS 的可读性。
3. BulletManager 从 Dictionary-per-projectile 迁移到类型化结构/SoA 与 swap-remove，预分配常用缓冲；
   UnitGrid 增量更新或分帧重建必须有命中等价测试。
4. MissileManager 维护活跃导弹表、source/target 索引与空间 broad-phase，替换 M×N 命中扫描及
   多处 `get_children()`；发射额度、过杀、穿透、AOE 与命中先后语义保持不变。
5. 以 S1 的 CIWS/VLS/Flak 最坏态校验；普通 C1 弹量不能代替弹幕证明。

P2 结束条件：G1 的 60 名全精度三次通过，并且 S1/S2 无行为回归。

### P3：战斗群级多战线

P3 是新系统，必须先写 approved spec。建议合同：

- 战斗群以 1–3 Hz 决定共同目标、攻击窗口、脱离、重整和增援；成员消费队级意图，
  不重复跑同一套全场选敌与态势树；
- 近景/玩家介入为精确层；中远距保留个体位置、可见飞行、开火节奏、烟迹和战线结果，
  决策与命中求解可以降频或批处理，但不能完全冻结；

## 13. UI / HUD 绘制域审计（2026-08-20）

### 13.1 测量方法

| 遮罩域 | avg FPS | p1 FPS | Canvas draw calls | Canvas primitives | 相对基线等效帧时 |
|---|---:|---:|---:|---:|---:|
| 无遮罩 | 92.15 | 61.16 | 803 | 24,871 | 10.85 ms |

| 世界文字 | 100.25 | 60.05 | 851 | 23,523 | 9.98 ms（约省 0.87 ms） |

draw-call 采样受窗口/驱动时序影响，单域数值不可相加；三轮稳定的 FPS 与 primitive 方向可裁决：固定 HUD
是当前最大的 UI 绘制块，世界文字第二，世界符号本身不是主要问题。无线电画面位于固定 HUD 遮罩中，
但 CSG 窗口只显示一条稀疏字幕，结合其 O(1) 计时器结构，没有证据把收益归因给无线电。

### 13.2 HUD 子域定位

固定 HUD 再拆成两轮反向顺序样本。右侧玩家仪表 + 僚机仪表组的平均 FPS 为 111.94，对照组为 82.31；
单独隐藏雷达为 92.60；底栏为 86.31。顶部时间/BOSS、击杀栏、威胁与受伤反馈没有稳定正收益。
子域短样本只用于排序，不作为新的毕业门数值。

代码路径解释了两处热点：

- `PlayerInstrumentPanel` 虽有 50 ms 数据重画门，但高度表指针移动会逐帧 `queue_redraw()`，从而把整块
  模块背景、大数字、武器文字、进度条与网格一起重提；`_draw()` 还会重复给 `TerminalGridOverlay` 写
  `line_color` / `regions`，而后者的 setter 即使值未变也无条件重画；
- `RadarDisplay` 每帧重画背景、三层 64 段圆环、十字、扫描线、15 条扫描尾迹，并扫描
  `CombatUnit.all_units` 生成 blip / 来袭弹警告。静态背景与动态 blip、60 Hz 扫描线目前共用一个
  CanvasItem，所以一条扫描线移动会让整个雷达重提。

### 13.3 节省方案优先级

1. `TerminalGridOverlay` setter 增加相等早退；`SurvivorHUD._layout_ui()` 改为 viewport / 面板尺寸 / 可见性
   dirty 时才重排，逐帧状态同步移出布局函数。
2. 玩家仪表拆成静态框板、10–20 Hz 数值层、独立 60 Hz 小指针/闪烁层；指针变化不得重画所有文字。
3. 雷达拆成 retained 静态底板、10–20 Hz blip 层和独立扫描线；圆环只在尺寸/配色变化时重建，扫描尾迹
   合为 `draw_multiline` 或轻量 shader，单位快照沿用低频缓存。
4. 世界标签继续按现有战略 LOD 保留玩家/BOSS/真实来袭豁免；下一步优先合并舰船/飞机标签文字提交，
   不隐藏战斗身份、锁定、无线电或技能反馈。

所有 A/B 遮罩与静态冻结代码在测量后已删除，没有进入正式运行路径。

战斗单位数量：

### 13.5 F3 运行时详细诊断面板

旧 F3 只显示少量人口与一秒性能桶，且会递归遍历场景树计数，无法回答“具体是哪类绘制或物理在烧帧”。
现已把同一入口扩成详细面板：打开时保留最近 120 个真实渲染帧，并以 4 Hz 刷新 avg / p95 / worst / `<60`；
同时显示 Godot 的 process / physics、Canvas draw calls / objects / primitives、2D active bodies / collision pairs /
islands、静态内存和对象/资源/节点数。

脚本侧按实际成本域拆分：飞机物理与 planner/kine/weapon/evade 子桶、AI/雷达、子弹/导弹、地面/舰船、
飞机标签/覆盖层/图标/特效、尾迹、导弹体/尾迹、HUD 总更新/玩家仪表/网格/雷达/威胁层、气氛、舰载
武器、音效、无线电、日志与生成。面板另列海陆空/挂点/弹丸/VFX 人口、BOSS 阶段、雷达 pair / 导弹
候选 / 技能事件 / 音效 / 无线电 / 日志调用率和前十 CPU 热点；技能持续效果按其实际消费方归入飞机物理、
武器、绘制或 VFX 桶，避免重复求和。父桶与子桶明确标注不可相加。F9 仍导出完整一秒桶与慢帧报告。

细分计时只在 F3 可见或 bench 慢帧追踪开启时执行，关闭 F3 即清空 120 帧历史并回到轻量路径，避免为了

## 14. 2026-08-22 · P0/G0 收口

本轮没有通过减员、缩短视距、关闭武器或隐藏战斗反馈过门。先修正 bench 慢帧追踪把“本帧 delta”错配到
下一帧工作量的观测错误，再保留最多 8 个尖峰的前 120 / 后 30 帧上下文，并输出 frame p95 / p99 / max、
