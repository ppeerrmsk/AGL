# 地图卡顿排查 R5：HUD 字形缓存与未闭环慢帧

日期：2026-09-18。承接 [R4](2026-09-18-map-repair-r4.md)。结论：**部分修复，整体性能未验收通过**。本轮没有改变地图风格、资源、分辨率、AO、MSAA、单位数量、武器或伤害逻辑。

## 1. 确认的原因与实装

诊断 `final_war_ocean_stress_20260918_103448.txt`：第116帧墙钟17.249ms，玩家HUD绘制8.064ms、武器区7.409ms，其中4次文字轮廓缓存未命中共6.614ms；地图CPU仅0.027ms。这证明该帧有字体冷路径，不能归咎于地图几何过多。

- `TerminalText.measure_ink_bounds` 保留完整 TextServer 塑形，增加最终字体RID/字号/glyph的2048项轮廓缓存，保留offset、连字和字体回退；环形逐项淘汰，不持有Font资源。
- `PlayerInstrumentPanel._configure_layout` 在真实MSDF字体与布局字号确定后，预热数字及`%`、`s`，避免第一次装填才走轮廓冷路径。正式HUD与预览共用，不是仅bench预热。
- 新增202种动态读数、三种字体与原始TextServer等价、容量上界及真实HUD预热测试。
- 仅诊断启用时增加导弹网格/碰撞/效果/快照，以及子弹视觉/网格/特殊弹/碰撞/伤害子桶；慢帧保留帧号和计数。子桶嵌套，不能与父桶相加算成本。

**被否定的捷径**：仅加glyph缓存的103959诊断仍有6.874ms文字未命中，因此再补真实HUD字体/字号预热。104333诊断仍有16.835ms慢帧，子弹根桶6.806ms，不能据此判断是碰撞还是伤害。104654诊断90秒墙钟最差16.293ms、慢帧0，也不能据一轮通过宣布完成。

## 3. 剩余问题：不要重复错误归因

追加36秒全CPU细分+渲染阶段诊断 `final_war_ocean_stress_20260918_110306.txt`，退出1。最差33.907ms：绘制前17.233ms、绘制中4.495ms、绘制后至下一帧12.179ms；HUD武器区14.162ms，**无文字轮廓缓存miss**。说明本次轮廓修复没有覆盖HUD全部慢路径。下一步需要分别量化排版查找、draw_string、武器读数计算，不得直接声称该14ms仍来自轮廓提取。

此诊断异步后端平均：根视口CPU2.510ms/GPU1.019ms，地图CPU0.134ms/GPU1.754ms，飞机CPU0.187ms/GPU0.580ms。它们不是同帧同步证据；绘制后阶段也包含物理处理，不能全部算作GPU等待。Engine.max_fps=0、VSync=1。GPU一次只读快照为30%利用率、1185MHz/P3；不足以认定电源策略根因，不改用户驱动设置。

第一轮304ms墙钟尖峰只有约十余ms已记CPU成本；同帧地图CPU0.094ms。CPU分桶不能解释全部停顿。默认采样与先前全细分诊断差异很大，但追加全细分也失败，不能简单归因采样模式，也不能把前面的较快诊断替代正式失败。

后续优先顺序：细分剩余HUD绘制尖峰 → 捕获未解释的帧间停顿 → 同批次重新验证。不要继续削地图美术、减少战斗负载或反复重跑直到偶然全绿。三图全边缘、长局及导出包的既有未验收边界仍保留。

## 4. 技术参考与工序

[Godot FontFile官方文档](https://docs.godotengine.org/en/stable/classes/class_fontfile.html)区分字形轮廓、光栅缓存与`render_range`；本轮实现只保证轮廓复用/布局预热，**没有证明消除全部首次光栅化/上传成本**。下一步若做光栅预热，需先建立可复现反例和等价测试。

全部引擎调用经bench wrapper，保留有限超时、原子锁与运行时错误门；运行期间不修改可扫描项目文件。没有提交/推送，也没有修改用户全局GPU设置。
