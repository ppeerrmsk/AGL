## 3. 本批真正积累的经验

### 3.1 把“地图闪烁”拆成可观测的不同问题

隐藏、缺覆盖、失格缩放、旧 PNG、镜头/合成错位、输入等待和长帧不是一个计数。每类都需要实际资源身份、提交切面及输入轨迹的证据。当前画面不闪，只能证明该段显示稳定；如果镜头被拖住、缩放终点没到或 SPACE 起距不足，测试仍未达到用户要的体验。

早期还纠正了表现层路由：配置正式 M20 后，旧二维栅格不能继续铺在下方，否则 3D 交接或透明区域会露出另一版地图。路由失败应报错并保持旧图关闭，不能以回退 PNG 掩盖失败。但“关闭旧 PNG”本身不修复 3D 缺覆盖，因此仍需独立检测覆盖和合成 alpha。该行为见 streaming spec §5.4，不能外推到 UGC 自带底图。

后台完成也不等于能显示。按既有合同依次验证字节可用、解码、引擎/GPU 就绪、资格/覆盖/预算，再提交；主线程提交时重验真实就绪和最新需求，保留旧绑定直到新绑定完整。过期、尚未完成和已证明无解必须分开，不能用旧代次的无解结果清掉新画面。未变身份的可见子集也不应每帧重复绑定、递增版本并让后台结果持续失效。

最早的 v29 缩远失败在 5000 ms 阶段终点实际 zoom 为 0.217468、目标为 0.2，最长准备等待 335 ms。记录显示先准备 9 页/44,361,608 字节的较小切面，再准备 2 页/87,623,704 字节的保护切面。它提示问题在选择和交接策略，不是简单“硬盘读慢”。

宽保护带候选在可用容量容纳两份显示切面时允许按原 96 MiB 显示上限重试，仍逐次验证联合资源、身份、清晰度和覆盖。不是把显示上限放宽到 384 MiB，也不是跳过就绪交接。动态镜头需要重新核验运动范围；旧结果不能因为已经算完就直接提交。

### 3.2 错峰要有服务时限，不能只以旧画面完整为准

main 的“同帧重活互斥”值得保留，但前提应包含最新输入需求。持续 WASD、快速缩远及 SPACE 返回都可能让旧切面很快失效。只有任务仍可延后、当前及所需运动范围有合格覆盖、输入等待仍在原合同内，才有资格让出本帧；暂停、取消和关闭排空也不能被饿死。

本批输入合同已有 **250 ms 准备等待目标**和 **500 ms 防卡死上限**，二者不能互换。33 次 SPACE 的首次响应、正常跟随插值收敛和地图准备等待也分别计量。保留正常跟随插值，不等于允许地图加载人为卡住镜头。

### 3.3 “加载过就保留”有价值，但必须保留资源所有权和预算语义

main 已有有界缓存和淘汰；反复加载不等于每次无条件丢弃。应先查：是首次请求、预算淘汰后重载、过期规划浪费，还是已加载资源换绑定。只靠总加载次数无法区分这些原因。

本批选用 384 MiB 的理由是保留更多可复用资源并改善输入等待，而非证明地图已全量常驻。384 档还沿用既有有界邻区预热，192 档不做该额外预热；因此三轮比较是**缓存档位策略整体比较**，不是“纯容量翻倍”的独立因果实验。没有容量与命中证据，不继续加预算或另建第二套缓存。

四种成本要分别记录：发布包字节、解压/加载暂存、运行池实际占用、当前显示切面成本。压缩包体不自动降低 GPU 上传成本；增加运行缓存不增加发布包体。预算账必须包含在途预约、旧新共同准备、节点持有和实际退役，不能只看最终可见页。本批沿用原三份纹理计费，没有通过少记资源获得通过。

### 3.4 先证明自动测试确实完成了动作

旧返回失败起距只有 29.52 屏幕像素，未达到原 100 像素下限。最初怀疑固定方向抵住地图边界，改为按边界选方向后，v31 三轮仍只有 12–16 像素，说明原假设不足。进一步确认正式升级面板释放了 WASD，而同阶段恢复后驱动没有重新按下。

v32 修复的是测试输入的暂停/恢复状态，加入相应回归；它本身**不是游戏 SPACE 卡顿修复**。33 次有效远距返回的最小起距为 1656.97 像素，三轮均经过正式模态并恢复。100 像素起距、250 ms 首次响应、1500 ms 收敛门均未放宽。后续任何自动操作都要同时记录请求动作、实际位移/缩放终点及中断恢复；不能以“发送过按键”代替触发证明。

模态期间的墙钟和可操控时间分别留存，仅真实关闭输入的正式模态可暂停输入计时；地图加载本身造成的停顿不能扣掉。显示异常审计在模态期间仍继续。

### 3.5 优化首次查询，而不是重复创造已有缓存

main 的 `tokyo_cell_stream` 已通过 `_known_resources` 复用确认存在的路径。候选仅对尚未确认的原生文件先作 `FileAccess.file_exists`，缺失或 `uid://` 等情况仍走原资源查询。真实加载、摘要验证、来源/覆盖资格以及导出重映射支持不变。

收益判断仍要靠同源对照。不能从“查询更快”直接推导“最慢帧更快”，更不能为了消除这段成本删除内容验证。10-17 handoff 中将检查移出热路径的方向可继续研究，但“安装时检查过就永远可信”不适用于可能重载或更换的编辑器候选。

### 3.7 先证明表示能装得下，再优化调度

早期实际 F5 反例与制作记录见 streaming spec §5.5，本次未重新制作或重跑这些历史测量：合法视角的原生 LOD4/5 分别有 258213/258347 个三角与视口相交，超过 240000 面上限。该统计发生在背面剔除/遮挡之前，不是可见像素数量；它仍说明保留全部原提交几何、只换空间分包不能保证所有视角可行。等待时间没有有限上界的 `no_solution`，不能靠更快线程或更久缓存治好。

用户随后允许概括普通街坊，须保留岸路、重要建筑和游戏对象，逐层核对来源与依赖；不能给省略后的几何复制旧覆盖标签。离散视角全部通过也不代表连续范围通过：历史 6974 个离散点的费用模型通过后，连续区间仍找到反例；中间包的正式规划结果也不能冒充完成树的结果。合理工序是先核表示与费用可行性，再检查连续覆盖，最后走正式规划、真实渲染和用户输入。

源几何证明、离线预算模型、运行时选择、实际绘制和人工观感各有证据范围。只降低三角数不能保证帧时变好；重分包可能增加页数、材质和上传次数，所以每次概括/拆分都要重新核联合成本与同条件性能。

### 3.8 包体优化与流送优化分开立项

main 的[地图分发规格](../specs/systems/tokyo-map-distribution.md)已有独立地图包、包内路径不变、逐文件摘要和启动挂载流程，应复用这些工序。本次没有测量新发行包大小，也没有验证新的压缩率；不能凭 2D/3D 类型或运行缓存大小推算发行体积。

若再做包体优化，先按正式依赖统计几何、纹理/mip、重复物理资源和临时候选占比，区分开发工作区与实际发行文件。移除未引用资产、改变编码或制作增量包，都须以真实包收据、回读摘要、导出程序从非程序目录启动及显示质量为证据。已有压缩资产是否值得再压，必须实测压缩率与解码/加载代价，不以压缩包下载体积代替 GPU 内存结论。

| 单次上传 CPU 最大值 ms | 6.239 | 8.323 | 加载变少并不保证单次上传变便宜 |

所有六轮 wrapper=1，显示异常为 0。统计只描述这三组观测，不声称统计显著性或未来帧上界。报告中的墙钟 `low1_fps` 是最慢 `ceil(1% × 样本数)` 帧平均时长的倒数；引擎 `p1_fps` 保持原口径，不混用。

东京 C1 的 384 档墙钟 5339 样本零慢帧、最大 16.576 ms，但引擎 delta 的 5340 样本仍有一帧低于 60、最差 56.23 FPS，因此严格门与 wrapper 仍失败。不能四舍五入或改选时钟将它变成通过。

192 档的六场输入审计也有零显示异常，但三轮 return 等待为 264/324/224 ms，前两轮超过 250 ms 目标。384 档的采用依据主要是更少加载与更短等待，**不是严格性能合格**。

### 4.1 阶段收益不能连乘，失败方案不要丢掉

| 阶段、独立对照 | 三轮慢帧合计 | 三轮全局最大帧 ms | 裁决 |
|---|---:|---:|---|
| v30 宽保护带关→开，192 MiB | 40→27 | 19.617→24.402 | 保留显式候选；慢帧减少但极值恶化 |
| v31 快速文件查询关→开，192 MiB | 49→23 | 23.810→28.096 | 保留显式候选；不是全体尾帧改善 |
| final-v32 缓存档192→384 | 33→26 | 25.123→23.280 | 选择人工候选，仍未验收 |
| v32 小上传额外单轮诊断 | 28 / 4327 样本 | 25.722 | 单轮未见收益，上传最大仍 6.361 ms；未纳入候选，不宣称普遍无效 |

这些阶段不是同一基线上的联合对照，不能把百分比相乘或把早期约 43 ms 与当前 23.280 ms 当成干净 A/B。小上传若要重开，须有新的页布局、上传粒度或驱动瓶颈证据；不能在同一输入上循环调参数。

## 5. 仍有改进空间，但按证据逐项推进

## 6. 对现有文档的改进与完成边界

本次已将可复用结论补回性能守则的采样/错峰部分，将输入有效性、四类验收、缓存与显示分账补入工程手册的实验模板，并从 Reference Index 提供入口。工程手册中的 R/M 旧阶段仍保留，增加历史标识；“最新状态”应由各图 spec 提供，不能让旧 R187 段落覆盖当前候选状态。

另修正工作区地图分发 spec 的两处残留：§2 已撤销旧固定增量包，但 §3.3 仍要求双包；三维资源缺失时的旧 PNG 回退描述也与 streaming spec 的正式 M20 路由不一致。现已按当前 `project.godot` 和已实现路由对齐，仅纠正文档，不修改默认入口或发布候选。这说明静态断链/锚点校验之外，还需要跨段落的默认状态和操作步骤一致性复核。

未来每轮最小记录应回答：**测了哪个版本；动作是否真实发生；四类门各自通过没有；收益在哪个统计口径成立；失败方案在什么新证据下才值得重开。** 新改动经 focused、默认 all、对应 Visual 三轮和实际 F5 后才能讨论推广。本文没有补跑游戏，也没有把已有候选默认开启。
