# 14 分钟成长基准与三轴机体成长审计

> 用固定种子 AI 实战回答“一局玩得较好能进化到哪一档”，并确认斗士、骑士、策士三线的机体自身确实随 Tier 变强。

## 1. 设计意图（Why）

- **体验目标**：以可重复数据决定 14 分钟局合理目标是 T3、T4 还是 T5，并量化小队人数增加带来的经验损失。
- **Litmus 自检**：成长必须能被玩家直接察觉；斗士尤其要兑现狗斗、机炮、硬生存，不能用导弹、flare 或随机技能冒充机体成长。
- **反模式规避**：不用单局最高值代表平衡；不用 Debug XP、无敌、强制升级或跳过资源；不预设首轮必须达到哪个等级。

## 2. 数据定义（What —— 全部数值，权威源）

### 2.1 测试矩阵

| 维度 | 值 |
|---|---|
| 起手机 | F-15 Eagle / F-14 Tomcat / A-6E Intruder / Mirage III |
| 小队规模 | 1 / 3 / 5 / 9 架，包含 ACE |
| 固定种子 | 每组合相同 20 个种子 |
| 总局数 | `4 × 4 × 20 = 320` |
| 单局时长 | 14:00 |
| 有效样本 | 存活到 14:00 且有效战斗时间 ≥80%；不足 20 个则补跑 |
| “较好一局” | 20 局最终等级 P75；同时报告 P50 / P90 |

地图、难度、敌人生成规则与输入强度固定；AI 正常索敌、攻击、规避、补给、进化与选卡，不得挂机。四条起手路线的轴选择脚本在运行前固定并随结果记录。

### 2.2 每组输出

| 字段 | 口径 |
|---|---|
| 最终等级 | 整数等级 + 当前升级进度%，P50/P75/P90 |
| 总 XP | P50 与 P75 |
| 击杀/分钟 | ACE 与僚机分列 |
| 首次进化 | T2 / T3 / T4 时间；未达到写 `—` |
| 卡点 | 等级不足 / 斗士不足 / 骑士不足 / 策士不足 |
| 结算站错过 | 因具体轴不足而错过一次进化的次数 |

### 2.3 三轴成长审计维度

| 轴 | 核心定位 | 必查维度 | 不可替代项 |
|---|---|---|---|
| 斗士 | 狗斗、机炮、硬生存 | HP/结构、持续 G、滚转、加减速；机炮伤害、射速、命中、弹药与装填；近身持续输出 | 导弹、flare、偶发随机技能 |
| 骑士 | 远程、雷达、导弹、机动生存 | 雷达距离/锥角、锁定效率、导弹挂载/性能、速度与脱离 | 只有导弹数量增加 |
| 策士 | 电子战、状态控制、团队增益 | 干扰/状态施加、传感器控制、团队收益、覆盖率与可靠性 | 只有文案、无运行时效果 |

## 3. 行为与公式（How）

### 3.1 基准统计

1. 对每个“起手机 × 小队规模”组合运行同一组 20 个种子。
2. 剔除未存活至 14:00 或有效战斗时间不足 80% 的样本，并用新种子补齐 20 个有效样本。
3. 对最终等级、总 XP、击杀/分钟与首次进化时间计算 P50/P75/P90。
4. 画四条“小队规模 → 14 分钟最终等级”曲线；报告 1 机到 9 机的等级损失与 XP 损失百分比。
5. 汇总“等级先到但轴不足”的累计等待时间与结算站错过次数，必须按具体缺轴分类。

运行器使用 Godot `--fixed-fps 60` 做**固定 60 Hz 加速模拟**：每个物理 tick、AI 决策、XP、死亡、选卡与门槛照常执行，只取消与墙钟的同步。840 秒指完整游戏时间，不允许缩短时长或抽样跳帧；这不是性能 FPS bench，性能数据不参与成长结论。

### 3.2 成长审计

- 按 T1→T5 分别选择斗士、骑士、策士代表链，比较每次换机前后的运行时参数与签名能力。
- 同时扫描全部同轴机体，避免只挑最好看的路线。
- 区分机体自身基数与玩家通用技能重放；审计结论不得把随机技能计入机体成长。
- 每个维度标为“增强 / 持平 / 倒退”。斗士线最终结论为：通过 / 部分通过 / 不通过。

#### 全角色机炮 Tier 基线（2026-08-26 重标）

机炮成长改为全角色共有的常规基线，再由攻击 / 机炮核心机上浮；不再要求所有斗士都使用强化档，
以免 T1→T2 第一步骤过陡。更强的既有特性可以高于常规基线，但每条真实进化边仍受 +35% 上限约束。

| Tier | `gun_damage_mult` | `gun_range_override` | `gun_cone_override` | `base_pilot_aim_skill` |
|---:|---:|---:|---:|---:|
| T2 | 1.175 | 1050m | 继承机型 | 0.65 |
| T3 | 1.25 | 1150m | 继承机型 | 0.70 |
| T4 | 1.35 | 1250m | 继承机型 | 0.75 |
| T5 | 1.45 | 1350m | 继承机型 | 0.80 |

强化档继续按 T2~T5 的 `1.30/1.40/1.50/1.60` 与 `1200/1300/1400/1500m` 表达机炮核心身份。

`fire_rate=3000 rpm` 与 `max_ammo=200` 保持全档共同基线：本轮只增强单发质量、可用射程、开火窗口和命中能力，避免射速、弹量与伤害同时相乘。正式验收以参数审计为准，不再要求 320 局实战样本。

## 4. 结构与组成（Structure）

- 一个可固定种子、固定路线、固定时长的 Shadow bench 场景。
- 一个批量调度脚本，生成 320 局与补跑任务并收集结构化结果。
- 一个聚合器，输出 CSV/JSON、分位数、曲线数据、卡点统计与结论。
- 一个静态参数审计器，读取 50 机档案、进化树与签名技能表生成三轴成长对照。

## 5. 验收标准（Acceptance / Litmus）

- [x] 用户取消 320 局实战批次；不得继续运行或用未完成样本得出结论。
- [x] 三轴静态成长对照覆盖 43 机；各轴逐 Tier 标出增强/持平/倒退。
- [x] 斗士 T2–T5 全部档案满足机炮 Tier 下限，且炮伤、射程、开火半角、瞄准四项逐档增强；43 机静态审计结论“通过”，违规项 0。
- [x] 基准只用正常规则，无 Debug XP、无敌、强制升级或资源跳过。
- [x] 性能：批量 bench 使用 Shadow 串行调度，不与 Godot editor 或其它 bench 争用锁。
- [x] 文档：本 spec 登记 `_INDEX.md`，静态审计状态与互动树已回填 Notion 审核页。
