# 三图战役串联与双队会师

> 单次战役依次穿过港湾、沙漠与海洋决战；前两图由两支不同的初始队伍分别成长，最后在第三图会师，并让玩家选择其中一套 build 作为主力。

## 1. 设计意图（Why）

- **体验目标**：把原本彼此独立的三张地图串成一段有前后因果的完整远征。玩家先后经营两套彼此独立的局内 build，最终选择主力并看到另一支队伍以僚机支援形式回归，让前两图的成长都在决战中获得可见回报。
- **Litmus 自检**：遵守设计哲学 3「信息察觉优先于数值」、7「战场氛围要热闹」、8「BOSS 战是真机制」与 9「局外成长要节制」。继承的价值必须通过不同队伍、武器、技能与决战阵容直接表现；本系统属于同一次战役内部的局内成长，不把 build 偷渡成永久局外数值。
- **反模式规避**：不把两套 build 合并成一份平均值；不允许第一图队伍直接跳到第二图继续滚雪球；不让顺延 BOSS 替换已经固定的地图主 BOSS；不把尚未定稿的沙漠敌人、任务或海洋决战任务擅自补完。

## 2. 数据定义（What —— 当前设计权威）

### 2.1 战役边界与术语

| 项 | 当前裁定 | 说明 |
|---|---|---|
| 单次战役长度 | 3 张地图 | 港湾 → 沙漠 → 海洋决战，顺序固定 |
| 常规地图 | 2 张 | 港湾、沙漠 |
| 决战地图 | 1 张 | 海洋决战 |
| 队伍存档槽 | 2 个 | `TEAM_A` 与 `TEAM_B`；各自保存独立 build 与队伍状态 |
| build 作用域 | 单支队伍、单次战役 | 不跨队共享，不写成局外永久成长 |
| 第三图角色 | `PRIMARY` + `SUPPORT` | 玩家从 A/B 中选择主力；未选中的队伍以僚机/支援形式登场 |
| 战役清零边界 | 新开一轮战役 | 三张地图之间不得因切图自动清空两队 build；放弃、失败与中途续玩语义见 §2.7 待定项 |

这里的“单局 / session / run”均指**完整三图战役**，不是单独一张地图。地图内部的临时战斗状态仍可独立清理，但不得误删战役级队伍快照与 BOSS 顺延账本。

### 2.2 固定地图顺序

| 阶段 | 玩家称呼 | 当前地图输入 | 出战队伍 | 地图主 BOSS | 内容状态 |
|---|---|---|---|---|---|
| 1 | 港湾 | 当前东京湾正式地图 | `TEAM_A`：第一支初始队伍 | **Mother Goose 固定** | 既有生存模式内容为起点；串联适配待设计 |
| 2 | 沙漠 | `desert_railway_preview` | `TEAM_B`：另一支初始队伍、另一架初始飞机 | **待定** | 敌人、战区任务与主 BOSS 均待后续填写 |
| 3 | 海洋决战 | `ocean_islands_preview` | 玩家在 A/B 中选一支为 `PRIMARY`；另一支为 `SUPPORT` | **Black Star 固定为最终 BOSS** | 决战任务结构待后续填写 |

`desert_railway_preview` 与 `ocean_islands_preview` 当前仍是可飞行预览输入；将其接入正式战役不自动批准任何敌人、任务、奖励或战区布点。

### 2.3 两支队伍与 build 快照

| 状态 | `TEAM_A` | `TEAM_B` |
|---|---|---|
| 战役开始 | 创建第一支初始队伍 | 预留第二支初始队伍槽；第二图开始时创建/启用 |
| 第一图 | 唯一可用队伍，正常积累自己的 build | 不可出战，也不接收 A 的奖励或 build |
| 第一图结束 | 冻结并保存 A 的队伍快照 | 保持未启用状态 |
| 第二图 | 不可出战 | 唯一可用队伍，从另一架初始飞机起步并积累自己的 build |
| 第二图结束 | 保留 A 快照 | 冻结并保存 B 的队伍快照 |
| 第三图 | 可被选为主力或支援 | 可被选为主力或支援 |

两份 build 必须保持独立。当前结构把以下内容视为队伍快照的组成方向，但具体逐字段序列化仍待定：

- 当前进化机型、三轴里程碑与技能栈；
- 已取得的局内特殊武器及其强化；
- 僚机编成与队伍身份；
- 其它明确属于“本次战役 build”的局内状态。

第三图选择只决定哪支队伍成为玩家主力，不做以下隐式操作：

- 不把 A/B 的技能栈、武器库或属性点求并集；
- 不把支援队 build 复制给主力队；
- 不把主力队 build 覆盖到支援队；
- 不因队伍成为 `SUPPORT` 就抹掉它在前图形成的 build 身份。

### 2.4 第三图会师

1. 第二图完成后进入一次主力选择。
2. 玩家在 `TEAM_A` 与 `TEAM_B` 两份已完成的 build 中选择一份作为 `PRIMARY`。
3. `PRIMARY` 成为第三图的玩家主力队伍。
4. 未选中的队伍以 `SUPPORT` 身份作为僚机/支援力量登场，并继续引用自己的 build 快照。
5. 两队共同进入海洋决战；Black Star 始终是这张图的最终 BOSS。

支援队的具体编成数量、入场时机、是否允许切控、是否占用现有 1–9 号机槽、战损与复活规则均未拍板，不在本版补值。

### 2.5 地图主 BOSS 分配

| 地图 | 固定裁定 | 不可被顺延机制改变的底线 |
|---|---|---|
| 港湾 | Mother Goose 留在第一图 | 不再迁往第二图 |
| 沙漠 | 主 BOSS 待定 | “火车”当前不占这个 BOSS 槽 |
| 海洋决战 | Black Star 固定 | 必须保持整段战役的最终 BOSS，不被顺延名单替换 |

沙漠“火车”方向改列为**关卡机制候选**：它在场景中移动，未来应与沙漠地图任务、铁路空间和战区机制一起设计；本 spec 只记录它不再作为当前沙漠 BOSS 方案，不定义尺寸、模块、路线、攻击方式或任务目标。

### 2.6 未遭遇 BOSS 的顺延账本

固定地图主 BOSS 与动态顺延名单分开记录：前者定义地图身份，后者保证前两图中没有遇到的 BOSS 不会被本次战役直接丢弃。

每次从前两张地图离开时，概念规则为：

```text
carry_out = (carry_in + 本图可遭遇 BOSS 集合) - 本图已遭遇 BOSS 集合
下一图 carry_in = 本图 carry_out
```

| 规则 | 当前裁定 |
|---|---|
| 顺延依据 | **是否遭遇**，不是历史击败次数，也不是 `boss-clear-progression` 的局外强化层 |
| 第一图未遭遇项 | 进入第二图顺延名单 |
| 第二图仍未遭遇项 | 继续进入第三图顺延名单 |
| 固定主 BOSS | 不被顺延项替换；Mother Goose 与 Black Star 的固定位置保持不变 |
| Black Star | 永远是最终 BOSS；顺延项在第三图中的插入位置与节奏待定 |

“遭遇”的精确定义（完成登场、正式进入交战、击败或其它门槛）、每图可遭遇 BOSS 池、顺延 BOSS 是追加战斗/事件插队/支线还是其它形态、第三图如何消化剩余名单，均列入 §2.7，后续由用户定稿。

### 2.7 明确保留的待定项

以下内容不是遗漏，而是本轮刻意留下的设计空位：

- 两支队伍各自使用哪一架初始飞机，以及是固定分配还是由玩家选择；唯一已定约束是两支队伍使用不同的初始飞机；
- build 快照的完整字段：HP、弹药、冷却、临时状态、僚机战损、未领取奖励等是否跨图；
- 地图失败、玩家阵亡、放弃战役、重试当前图时采用回滚、保留还是整轮结束；
- 是否允许退出游戏后从图间检查点继续，以及战役存档格式、槽位数与写盘时机；
- 第一图当前生存模式内容怎样收束为可进入第二图的明确通关条件；
- 沙漠图敌人、战区任务、地图机制、主 BOSS 与火车机制的全部细节；
- 海洋决战的任务阶段、两队会师演出、支援队控制权与 Black Star 前的战斗结构；
- 动态 BOSS 池、遭遇判定、顺延插入位置、同图数量上限与第三图剩余项处理；
- 每图结算、功勋入账与整段战役最终结算的边界。

## 3. 行为与状态流（How）

### 3.1 战役主状态机

| 状态 | 进入条件 | 必须保留/产生的结果 | 下一状态 |
|---|---|---|---|
| `CAMPAIGN_START` | 新开三图战役 | 清空旧战役态；建立 A/B 槽与 BOSS 顺延账本 | `HARBOR_ACTIVE` |
| `HARBOR_ACTIVE` | 创建 `TEAM_A` | 只允许 A 出战并积累 A build | `HARBOR_CLEAR` |
| `HARBOR_CLEAR` | 港湾通关 | 保存 A；结算第一图未遭遇 BOSS | `DESERT_ACTIVE` |
| `DESERT_ACTIVE` | 创建/启用 `TEAM_B` | 只允许 B 出战并积累 B build；A 保持冻结 | `DESERT_CLEAR` |
| `DESERT_CLEAR` | 沙漠通关 | 保存 B；再次结算未遭遇 BOSS | `FINAL_PRIMARY_SELECT` |
| `FINAL_PRIMARY_SELECT` | A/B 两份快照都存在 | 玩家选择主力；另一队绑定为支援 | `OCEAN_FINAL_ACTIVE` |
| `OCEAN_FINAL_ACTIVE` | 两队会师完成 | 主力可控、支援按自身 build 登场；处理第三图任务与顺延 BOSS | `BLACK_STAR_FINAL` |
| `BLACK_STAR_FINAL` | 最终战触发 | 固定生成 Black Star，不接受动态替换 | `CAMPAIGN_CLEAR` |
| `CAMPAIGN_CLEAR` | Black Star 被击败 | 完成整段战役结算；关闭本次战役态 | 局外流程 |

### 3.2 跨图切换硬规则

- 切图前先冻结当前队伍快照，再清理地图场景；不得依赖旧场景节点继续存活来“继承”。
- 第二图初始化只能读取 `TEAM_B` 与战役公共账本，不得把 `TEAM_A` 当当前玩家队伍复用。
- 第三图同时恢复两份快照，但主力/支援角色必须显式指定；不得用“最后一张图加载了哪支队伍”隐式决定。
- BOSS 顺延账本属于战役公共态，不属于 A 或 B，因此换队不会清空。
- 局外生涯档案、BOSS 历史强化与功勋账本仍是独立持久层；不得把它们混入 A/B build 快照。

## 4. 结构与组成（Structure）

| 组成 | 职责 | 当前状态 |
|---|---|---|
| `CampaignRunState` | 当前阶段、两支队伍快照、主力选择、完成地图、顺延账本 | 仅设计占位，未实装 |
| `TeamRunState[TEAM_A/TEAM_B]` | 单队起手机身份、build、武器库、进化与编成快照 | 字段边界待 §2.7 定稿 |
| `CampaignStageDef[3]` | 固定地图顺序、允许队伍、主 BOSS 锚点、内容入口 | 港湾/沙漠/海洋顺序已定 |
| `BossTransferLedger` | 记录可遭遇、已遭遇与待顺延 BOSS | 规则骨架已定，池与判定待定 |
| `FinalRendezvous` | A/B 主力选择与支援恢复 | 角色关系已定，战斗/UI 细节待定 |

职责边界：

- 本 spec 只管**整段三图战役的编排、继承和会师**。
- [map-2-3-preview](map-2-3-preview.md) 继续管两张新地图的地理、渲染与空图试飞，不在其中塞任务或 build 规则。
- 各 BOSS 的战斗数值与机制仍由各自 BOSS spec 管；本 spec 只决定战役中的固定位置与顺延关系。
- 沙漠敌人/任务、火车机制与海洋决战任务应在用户逐步定稿时建立各自内容 spec，并由本 spec 引用，不在这里提前代写。

## 5. 验收标准（Acceptance / Litmus）

- [ ] 战役入口严格按港湾 → 沙漠 → 海洋决战推进，不允许在本模式中跳序。
- [ ] 第一图只能使用 `TEAM_A`；第二图只能使用不同初始飞机起步的 `TEAM_B`，A 的 build 不渗入 B。
- [ ] 两图完成后同时存在两份可核对的独立 build；第三图由玩家明确选择主力，另一队按自身 build 作为支援登场。
- [ ] Mother Goose 固定在第一图；Black Star 固定为第三图最终 BOSS；沙漠 BOSS 未定时系统不擅自回退随机固定值。
- [ ] 前两图未遭遇的动态 BOSS 会进入下一图顺延账本，且不会覆盖固定主 BOSS。
- [ ] 火车不登记为沙漠 BOSS；未来只从沙漠关卡机制/任务方向继续设计。
- [ ] 中途保存/读取后，两份 build、当前地图、主力选择与顺延账本不会串槽或丢失（保存语义定稿后执行）。
- [ ] 所有 §2.7 空位在未拍板前保持显式待定，不由实现侧默认值反向定义设计。
- [ ] 性能：两队会师与顺延 BOSS 的最坏实体规模在实现阶段跑 Sentinel + Lv5+ 压测，FPS 掉幅 < 15。
- [ ] 已知 seam：跨场景只保存纯数据，不持有已释放 Godot 对象；恢复玩家引用必须走统一 chokepoint。
- [ ] i18n：地图阶段名、主力选择、会师、顺延提示与结算文案全部走正式三语表。
- [ ] 文档：本 spec 已登记 `_INDEX`；后续内容 spec 只填各自职责，不建立并行三图总流程文档。
