# AGL 设计审问

把模糊想法收敛成可进入 AGL spec-first 流程的设计契约。用户做产品决定；仓库事实由 Codex 查证。

## 权威与边界

- 当前用户要求优先；项目约定以根目录 `AGENTS.md` 为入口。
- 新机制、数值、敌人、技能、BOSS 或系统必须遵循 `docs/DESIGN_PHILOSOPHY.md` 与 `docs/specs/` 的 SSOT 分工。UI 走 `AGENTS.md` 规定的 UI 例外。
- 本 skill 不写 spec、不改代码、不创建 Issue、不建分支、不提交。只有用户另行要求相应动作时，才进入正常工作流。
- 不询问能从仓库、日志或工具查到的事实。按 `docs/reference/_INDEX.md` → Script Index / Code Index → 定点读取的路径调查。

## 决策循环

1. 先用一小段话列出已经确定的目标、约束和仍会实质改变结果的决策。
2. 每轮只提出一个当前依赖链上最靠前的决定，附推荐答案和主要取舍。答案会改变后续问题时，不提前追问下游分支。
3. 用户回答后重新计算尚未决定的分支。发现术语与现有 spec 或代码矛盾时，给出证据并让用户裁决，不自行改写产品意图。
4. 用具体场景压力测试边界，包括正常路径、失败路径、重入/取消、极端负载和玩家看不见反馈的情况；只问与当前设计有关的分支。

## AGL 检查面

按任务相关性覆盖：

- 玩家循环、成功/失败条件、首次体验与重复游玩的差异。
- 行为和数值的权威 owner、单一数据源及跨层消费路径。
- 玩家可见的 HUD、世界反馈、声音和状态可读性。
- 正式局之外的 Debug 可达性，以及是否真实触发运行时条件。
- 生命周期终态、缓存清理、切控/阵营转换和下一帧消费者。
- 60 FPS 预算、实体数扩展形状、降频/冻结/简化策略及豁免对象。
- i18n、Visual/实机验收与 headless 技术证明的边界。

## 完成条件

当所有会改变行为、数值、架构、范围或验收的决策都已确定时，输出一份精炼的 spec-ready 摘要：设计意图、行为与数值、状态/失败路径、验收、明确不做的内容，以及仍需证据校准而非拍脑袋决定的项目。最后请用户确认是否已经形成共同理解；未确认前不进入实现。
