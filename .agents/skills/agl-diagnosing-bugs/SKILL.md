# AGL 缺陷诊断

目标是确认真正的 authority path 和根因，并用与用户症状一致的信号证明它，而不是先猜一个补丁。

当前用户要求和根目录 `AGENTS.md` 优先于本 skill。若出现冲突，按前两者执行，并在结果中指出触发冲突的具体 skill 条款。

## 权限与证据边界

- 区分“诊断”和“修复”。用户只要求诊断时，保持代码和外部状态不变；需要临时插桩或修复时先取得明确授权。
- 输出命令、日志或捕获物前去除密钥、令牌、个人信息与认证头，只保留承载信号的内容。
- Headless 通过不等于 Visual 或实际游玩通过。分别报告实现状态、技术验证和完整玩家流程。

## 1. 定位真实 owner

先读 `AGENTS.md` 中与问题有关的硬约定，再走 `docs/reference/_INDEX.md` → `script-index.md` / `code-index.md` → 50–100 行定点读取。画出最短 authority path：输入或事件 → controller/data owner → renderer/HUD 或消费者 → 生命周期终态。

为了选择正确 seam，可以在建立复现命令前做有限的代码与日志调查；不得把阅读得到的“看起来可疑”当作根因。

## 2. 建立反馈信号

优先复用现有 focused BenchRunner 场景、正式 signal/终态入口或可重复 Visual fixture。信号必须能捕获用户描述的具体错误，而不只是“不崩溃”。

- Godot 只能通过 `bench/run.cmd` / `bench/run.sh` 启动，使用 4.7+、有限超时和项目锁。
- 锁被占用时等待占用者自然退出后重跑；不绕过、不偷锁、不结束可能含未保存内容的编辑器。
- 新探针或临时产物只放 `tmp/`；Godot 会扫描的目录中不得边写资源边启动引擎。
- Visual 问题优先构造 Visual 证据；无法自动化时，明确记录最小人工复现步骤和尚缺的证明。

如果无法建立可信信号，列出已尝试的路径和缺少的输入，不继续给出伪确定根因。

## 3. 复现、缩小与假设

确认信号复现的是同一个症状，然后逐项缩小数据、实体、状态和时间窗口。提出 3–5 个按证据排序、可证伪的假设；每个假设写出若它为真应观察到什么。向用户简要同步排序，但安全的只读验证可继续进行。

## 4. 验证与插桩

一次只改变一个变量。优先使用现有 EventLogger、bench 结果、状态快照与性能分桶。只有获得写入授权后才加临时插桩；插桩统一使用可搜索的 `[DEBUG-<id>]` 前缀，并在交付前删除。

性能问题先测量基线和成本随实体数的增长形状，再考虑修改。不得通过删除战斗单位、武器、伤害或反馈来换取通过。

## 5. 修复和回归（仅在已授权时）

在能覆盖真实调用模式的 seam 上先加入会失败的回归，再做最小修复。生命周期问题必须走正式伤害/signal/终态入口，终态后至少继续一个 SceneTree 帧并跨过下一次缓存消费。

验证顺序按任务风险选择：最窄 focused → 生命周期专项（如适用）→ `bench/run.cmd all 1 300 Shadow Headless`。涉及可见反馈或性能时，再执行对应 Visual/压力验收；任何退出码 86 从首个 `RUNTIME ERROR` 块处理。

## 完成条件

报告用户症状、真实 owner、根因、排除过的主要假设、复现/回归证据，以及尚未完成的 Visual 或实机验收。若实施了修改，还要确认临时插桩已清除、相关索引和文档已同步，并保持无关脏改动不变。
